# Controller-only execution

Gameplay always goes through the existing bounded pad gateway. The Astra mod adds read-only UI focus and card-instance observations, not action endpoints.

- Prefer play actions keyed by observed card instance_id. The executor computes the complete hand-navigation segment from observed card indices, verifies its destination once, then checks selection and completed play. A transport failure immediately cancels the remainder.
- Self/all-target cards and multi-enemy targeting use the card helper. It verifies the selected card and enemy combat identity before confirming. Ally-target cards still use bounded observed navigation.
- In this game build, controller A first selects a card and then confirms it, including Defend. Null Godot focus can mean a self-target card is selected, not lost controller input. Read `in_card_play` and `selected_card`; never blindly double-A or navigate the hand during targeting.
- Do not assume first-card/last-card focus or stable hand indices. The read-only sensor uses collision-free card-instance identities and reports target positions/hittability.
- A plan contains at most eight cards/actions. Draws, random effects, choices, replay, return-to-hand effects, or unexpected hand changes stop the batch.
- UI navigation permits 1–12 d-pad presses per sequence, with one fresh STS2MCP check at its boundary. Navigation and activation can share a model decision as separate actions when exact destination focus/preconditions are known. Each later action requires a checked screen/focus; unknown transitions, purchases, event choices and abandonment end the plan. Only known Singleplayer → Standard → character-select transitions may continue after activation, and each is observed and verified. A selects, B cancels, Y ends turn/proceeds, X enters the top panel/potions. The card helper batches verified combat inputs without model calls.
- Be fast with low-risk UI hypotheses: one brief prediction, bounded direction input, fresh state. Do not reanalyze the route or screenshot before every button. This permission ends at the first actual failure or contradictory evidence; it is not permission to experiment around a bug.
- `scout` scrolls a map using joystick up/down, left/right stick, 100–600 ms; gateway releases automatically. Up is y=-1, down is y=+1. Camera scrolling may leave mod JSON unchanged: inspect the next screenshot, not just the transport acknowledgement. Do not repeat an unchanged-view scout indefinitely.
- Prefer `map.nodes` and `next_options` over screenshot route tracing. Repeated focus moves omit the unchanged full graph once a strategy exists; keep the chosen route in the compact strategy. `map.current_position` is the last visited run location, not UI focus; a next node may already be highlighted. Sensor v2 lacks focused map-node coordinates; numeric Godot node suffixes are not map columns. Screenshots remain necessary for that focus gap.
- Animation waits and cheap state checks stay inside the executor. Legal free cards can remain at zero energy.
- At startup abandon an existing run and confirm, then Singleplayer/Standard, requested character/ascension, Embark; verify floor 1. Never continue an old run.
- Stale plans, repeated identical plans and prolonged lack of progress pause instead of generating unbounded inputs.
- A failed focus movement or the first action/API/planner error pauses immediately. Do not repeat the input, back out, play a different card or end turn to debug. Use report_issue for contradictory state, unsupported/risky activations or suspected bugs, not simply an untested reversible focus hypothesis.
- Reloading the player does not restart the game. Resume only the supervisor-reviewed interaction from fresh state; do not repeat the initial abandon/startup sequence.
